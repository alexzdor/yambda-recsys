# Рекомендации музыки на Yambda (50M)

Пет-проект: рекомендательная система на открытом датасете Яндекс Музыки "Yambda".
Задача: по истории прослушиваний предсказать, какие треки пользователь послушает в ближайшие сутки.

## Данные

- Yambda, версия 50M, таблица `listens` (формат `flat`).
- Положительный пример: прослушивание с `played_ratio_pct >= 50`.
- Таймстемпы в секундах, период около 300 дней.

## Протокол оценки

- **Разбиение по времени.** Train это всё до момента отсечки (минус зазор 30 минут), target это сутки после неё.
- **Тест:** последние сутки. Размер train: 29 280 230 событий, test: 157 696 событий.
- **Validation:** сутки перед тестом. Гиперпараметры подбираются на трёх отсечках (`test_start - 1, 2, 3 суток`) с усреднением, тест открывается один раз.
- **Холодный старт:** 4599 из 4600 тестовых пользователей есть в train, поэтому в проекте он не рассматривается.
- **Метрики:** Recall@100 и NDCG@100, усреднение по пользователям.

### Две постановки

| Постановка | Повторы | Что измеряет |
|---|---|---|
| **A. «Что включит»** | разрешены, полный `truth` | угадывание поведения пользователя |
| **B. «Что откроет нового»** | запрещены, из `truth` убраны уже слышанные треки | поиск нового |

## Ключевое наблюдение: повторы

В validation **66.9% пар (пользователь, трек) это повторы** уже слышанного в train.
У 3507 из 4625 пользователей (76%) есть хотя бы один новый трек.
Поэтому в постановке A главный источник правильных ответов это собственная история пользователя.

## Результаты

### Постановка A («что включит»)

| Модель | Recall@100 | NDCG@100 | Где измерено |
|---|---|---|---|
| Popular, вся история | 0.0335 | 0.0219 | validation, 1 отсечка |
| Popular, окно 1 день | 0.0539 | 0.0339 | validation, 3 отсечки |
| iALS (дефолт) | 0.1060 | 0.0645 | validation, 1 отсечка |
| Мои топ-треки (счётчик) | 0.2693 | 0.1730 | validation, 3 отсечки |
| Мои топ-треки, затухание τ=14 | 0.3240 | 0.2499 | validation, 3 отсечки |
| Мои топ-треки, затухание τ=30 | 0.3338 | 0.2448 | validation, 3 отсечки |

Тест (окно 1 день, выбрано по validation): Recall 0.0531, NDCG 0.0330.
Тест для остальных моделей будет посчитан один раз в конце.

**Подбор окна популярного** (validation, 3 отсечки): окна 0.25 / 0.5 / 1 / 3 дня дают Recall 0.0469 / 0.0528 / 0.0539 / 0.0534. Выбрано 1 день, разница с 3 днями в пределах шума.

**Подбор τ для затухания** (веса `exp(-Δt/τ)`, validation, 3 отсечки):

| τ (дней) | Recall@100 | NDCG@100 |
|---|---|---|
| 0.5 | 0.2930 | 0.2176 |
| 1 | 0.2947 | 0.2254 |
| 3 | 0.3006 | 0.2390 |
| 7 | 0.3120 | 0.2479 |
| 14 | 0.3240 | 0.2499 |
| 30 | 0.3338 | 0.2448 |
| 100 | 0.3174 | 0.2166 |

Критерий выбора зафиксирован заранее: NDCG@100, поэтому основным взят τ=14. Затухание даёт примерно +20% к Recall и +44% к NDCG относительно простого счётчика.

### Постановка B («новое»), validation, 1 отсечка

| Модель | Recall@100 | NDCG@100 |
|---|---|---|
| Popular, окно 1 день, без повторов | 0.0611 | 0.0315 |
| iALS (дефолт), без повторов | 0.0656 | 0.0286 |

iALS с дефолтными параметрами не лучше свежего популярного (разница в пределах шума). Идёт подбор гиперпараметров.

## Выводы

1. Простой персональный бейзлайн с затуханием по времени сильно обгоняет и популярное, и iALS: пользователи в основном переслушивают своё, и недавность важна.
2. iALS «из коробки» плохо ловит повторы и в постановке B не лучше популярного.
3. Офлайн-метрики измеряют угадывание наблюдавшегося поведения, а не пользу рекомендаций. Финальную проверку дал бы только A/B-тест.

## Ошибки, найденные по ходу (и исправленные)

- Беззнаковый тип `timestamp` приводил к переполнению в `exp` и мусорным метрикам. Исправлено приведением к `float64` и `assert` на конечность весов.
- В `eval_als` игнорировался параметр `cutoff` (метрики считались по чужому `truth`). Исправлено.
- Метод «Popular за N дней» это жёсткое окно, а не затухание. Настоящее затухание реализовано отдельно для истории пользователя.
