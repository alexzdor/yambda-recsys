# Рекомендации музыки на Yambda (50M)

Пет-проект: двухстадийная рекомендательная система на открытом датасете Яндекс Музыки
([Yambda](https://huggingface.co/datasets/yandex/yambda)).
Задача: по истории прослушиваний предсказать, какие треки пользователь послушает в ближайшие сутки.

## Главный результат

CatBoost-ранкер (YetiRank) на тесте: **Recall@100 = 0.364, NDCG@100 = 0.284**.
Это на 13% (Recall) и 16% (NDCG) выше сортировки по взвешенной истории на тех же кандидатах
и в 6.8 раза выше Recall популярного за последний день (0.053).

## Данные

- Yambda, версия 50M, таблица `listens` (формат `flat`).
- Положительный пример: прослушивание с `played_ratio_pct >= 50`.
- Таймстемпы в секундах, период около 300 дней.

## Протокол оценки

- **Разбиение по времени.** Признаки считаются по данным до отсечки (с зазором 30 минут), цель: сутки после неё.
- **Тест:** последние сутки. В подбор параметров не попадал, открыт один раз.
- **Validation:** отсечки за 1, 2, 3 суток до теста, подбор параметров с усреднением.
- **Ранкер:** обучение на отсечках shift 2-4, проверка на shift 1. Финал: переобучение на shift 1-4, один запуск на тесте.
- **Холодный старт:** 4599 из 4600 тестовых пользователей есть в train, поэтому не рассматривается.
- **Метрики:** Recall@100 и NDCG@100, усреднение по пользователям, считаются по полному `truth`.

### Две постановки

| Постановка | Повторы | Что измеряет |
|---|---|---|
| **A. «Что включит»** | разрешены | угадывание поведения пользователя |
| **B. «Что откроет нового»** | запрещены, из `truth` убраны слышанные треки | поиск нового |

Финальная система оценивалась в постановке A. Постановка B использовалась для подбора iALS.

## Ключевое наблюдение: повторы

На validation **66.9% пар (пользователь, трек) это повторы** уже слышанного.
Поэтому простое «топ твоих треков» (Recall 0.266) в 2.5 раза обгоняет iALS «из коробки» (0.106):
основной источник правильных ответов это история пользователя.

## Архитектура

1. **Кандидаты (около 620 на пользователя):**
   - топ-500 из истории по весу с затуханием (τ=14);
   - топ-100 новых треков от iALS (factors=256, alpha=0.3);
   - топ-100 популярного за последние сутки.
2. **Ранкер:** `CatBoostRanker` (YetiRank), 19 признаков, 200 деревьев, lr=0.15, depth=6.
   В обучении все `y=1` и 25% случайных негативов.
3. **Признаки** (посчитаны только по данным до отсечки):
   - пара пользователь-трек: число прослушиваний, давность последнего, веса `w1..w100` (сумма `exp(-Δt/τ)` по прослушиваниям), ранг в истории, доля трека в истории;
   - трек: популярность за всё время, 7 дней, 1 день;
   - iALS: ранг и скор;
   - пользователь: активность, число разных треков.

`uid` и `item_id` в признаки не подаются.

**Потолок кандидатов:** на validation общий candidate recall равен 0.5995, Recall@100 ранкера не может его превысить.

## Результаты на тесте (постановка A)

| Модель | Recall@100 | NDCG@100 |
|---|---|---|
| Popular, последний 1 день | 0.0531 | 0.0330 |
| Мои топ-треки (счётчик) | 0.2663 | 0.1690 |
| Мои топ-треки, затухание τ=14 (топ-100 по всей истории) | 0.3197 | 0.2441 |
| Сортировка кандидатов по `w14` | 0.3213 | 0.2446 |
| **YetiRank (среднее по 3 seed'ам)** | **0.3635** | **0.2839** |

- Разброс YetiRank между seed'ами: std 0.0003 (Recall) и 0.0004 (NDCG).
- Чистое сравнение: `w14` и YetiRank работают на одних и тех же кандидатах. Выигрыш ранкера: +13.2% Recall, +16.1% NDCG.
- Валидация и тест согласуются (на validation выигрыш около 15%), то есть выбор конфигурации не переобучен.
- Строка «затухание τ=14» берёт топ-100 по всей истории, а не по кандидатам, поэтому чуть отличается от `w14`.

## Подбор параметров (validation)

- **Окно популярного** (жёсткое окно, не затухание): 0.25 / 0.5 / 1 / 3 дня, выбран 1 день.
- **τ затухания** (3 отсечки):

| τ (дней) | Recall@100 | NDCG@100 |
|---|---|---|
| 0.5 | 0.2930 | 0.2176 |
| 1 | 0.2947 | 0.2254 |
| 3 | 0.3006 | 0.2390 |
| 7 | 0.3120 | 0.2479 |
| 14 | 0.3240 | 0.2499 |
| 30 | 0.3338 | 0.2448 |
| 100 | 0.3174 | 0.2166 |

  Критерий (NDCG) зафиксирован заранее, поэтому выбран τ=14. Для сравнения, простой счётчик даёт 0.2693 / 0.1730, то есть затухание добавляет около +20% Recall и +44% NDCG.
- **iALS (постановка B, 3 отсечки):** NDCG растёт с `factors` (64 → 128 → 256 → 512: 0.0279 → 0.0311 → 0.0336 → 0.0354) и не насыщается. Выбрано 256 из-за времени обучения (около 5 минут). `alpha` 0.3-1 лучше больших значений, `reg` почти не влияет.
  Настроенный iALS лучше свежего популярного без повторов: Recall 0.0777 против 0.0591, NDCG 0.0336 против 0.0293.
- **Число кандидатов из истории:** топ-200 покрывает 57% повторов, топ-500 покрывает 82%, топ-1000 покрывает 94%. Выбрано 500.

## Ablation (validation, shift 1)

Классификатор CatBoost, 200 деревьев, одинаковые настройки во всех запусках. Шум между seed'ами: около 0.0005 NDCG.

| Что убрали | Recall@100 | NDCG@100 | Δ NDCG |
|---|---|---|---|
| ничего (seed 42 / 43) | 0.3623 / 0.3632 | 0.2834 / 0.2839 | - |
| iALS (`als_*`) | 0.3621 | 0.2833 | -0.0001 |
| популярность треков | 0.3617 | 0.2827 | -0.0007 |
| несколько τ (`w1, w7, w30, w100`) | 0.3613 | 0.2821 | -0.0013 |
| признаки пользователя | 0.3615 | 0.2791 | -0.0043 |
| доп. признаки истории | 0.3581 | 0.2803 | -0.0032 |

- Прирост над `w14` распределён по признакам истории и не держится на одной группе.
- iALS как признак измеримого вклада не дал (как источник кандидатов он нужен для новых треков).
- Признаки внутри групп взаимозаменяемы, поэтому «не упало» означает «не нужно при остальных признаках».
- Шум оценён по двум seed'ам, разницы порядка 0.001 нельзя считать эффектом.

## Выводы

1. Задача в основном про повторы: персональная история с затуханием по времени сильно обгоняет и популярное, и iALS.
2. Недавность прослушивания несёт сильный сигнал: затухание заметно лучше обычного счётчика.
3. Двухстадийная схема с ранкером добавляет примерно +13-16% к лучшей одиночной формуле.
4. YetiRank немного лучше обычного классификатора (на validation 0.3706 / 0.2882 против 0.3623 / 0.2834, один seed).
5. iALS «из коробки» не лучше популярного, после подбора `factors` лучше.

## Ограничения

- Офлайн-метрики измеряют угадывание наблюдавшегося поведения, а не пользу рекомендаций. Финальную проверку дал бы только A/B-тест.
- Один тестовый день и около 4.6k пользователей, доверительные интервалы не считались.
- Ранкер на тесте в постановке B не оценивался.
- Ablation сделан на классификаторе, а не на финальном ранкере, и на одной отсечке.
- Не использовались лайки и дизлайки, аудио-эмбеддинги, информация об артистах и альбомах.
- iALS настраивался до `factors=512`, оптимум не достигнут.

## Ошибки по ходу (исправлены)

- Беззнаковый `timestamp` давал переполнение в `exp`: исправлено приведением к `float64` и проверкой на конечность весов.
- В `eval_als` игнорировался параметр `cutoff`: исправлено.
- «Popular за N дней» это жёсткое окно, а не затухание. Настоящее затухание реализовано для истории пользователя.
